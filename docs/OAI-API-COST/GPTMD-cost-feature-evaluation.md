# GPTMD OpenAI cost feature evaluation

**Reviewed:** 2026-10-06
**Starting source:** `using oai api in a app, are there special pricing or service for this - Google Search.html`
**Scope:** Pay-as-you-go API access, prompt caching, and the Batch API.

The Google Search capture is useful for identifying options, but its savings ranges and account-tier statements are not treated as authoritative. The decisions below use current OpenAI API documentation and GPTMD's checked-in request paths.

## Findings

| Feature | OpenAI behavior | GPTMD fit | Decision |
| --- | --- | --- | --- |
| Pay-as-you-go | API access is billed by model, token category, and processing tier. Moving to a pay-as-you-go usage tier can raise rate limits; it does not itself discount token prices. Organization spend limits apply across projects, so they are not a per-tenant GPTMD budget. | GPTMD already makes Responses API calls and records per-response token usage plus a versioned public-rate estimate under `q15`. Tenant session/response quotas exist, but are count quotas rather than dollar budgets. | Keep API pay-as-you-go as the provider billing basis. Use GPTMD's tenant-scoped cost estimates for app budgets and OpenAI's organization controls as a separate account-level guard. Do not advertise pay-as-you-go as a discount. |
| Prompt caching | Enabled by default on supported models. Repeated matching prefixes receive the model's cached-input rate. For GPT-6 Luna, current Standard rates per million tokens are $0.10 uncached input, $0.01 cached input, and $0.125 cache-write input. A write plus nine full reads of the same 10,000-token prefix costs about $0.00215 versus $0.01 for ten uncached passes, an illustrative 78.5% reduction on that repeated prefix. Output and changing suffix tokens are not discounted by this calculation. | Strong fit. Scenario setup sends stable setup instructions and the complete canonical PP JSON before the varying scenario seed, with the structured output schema retained. Two synthetic GPT-6 Luna setup responses reported 1,938 and 1,936 input tokens, each with 1,880 cached input tokens; this confirms the marked stable prefix cleared the 1,024-token eligibility threshold and was reused. The responses had no cache-write tokens because the prefix was already warm for this measurement. Patient turns send the stable developer policy before changing learner/scenario content. | Scenario setup now sets `prompt_cache_options.mode: "explicit"`, TTL `30m`, and `prompt_cache_breakpoint: { mode: "explicit" }` at the end of the stable developer content. This makes the write boundary explicit and leaves the seed after it. GPT-6 Luna does not need a `prompt_cache_key`; OpenAI routes GPT-5.6-and-later caching automatically. Do not set a longer retention policy. The check used synthetic provider requests and did not create learner sessions or a production hit-rate baseline. |
| Batch API | Asynchronous requests support `/v1/responses`, cost 50% less than synchronous API calls, and complete within 24 hours. Each request needs a unique `custom_id`; results may be returned in a different order. Current limits include 50,000 requests and a 200 MB input file per batch. | Not suitable for the active patient conversation or session setup path, which must return a response during the learner's visit. It is a strong candidate for a future offline evaluation lane: synthetic case/profile generation, prompt regression runs, and rubric scoring after the assessment rubric is approved. No educator-approved gold case set or implemented scoring rubric currently exists, and current scenario generation uses Conversations plus validation/cleanup behavior that a stateless batch evaluator would need to model explicitly. Batch input/output files also introduce a provider-side artifact lifecycle; output files are automatically deleted 30 days after completion. | Defer product integration until a synthetic, educator-reviewed evaluation set and rubric exist. Then use standalone `/v1/responses` batch requests with `custom_id` mapped to a fixture/version, never with learner or patient data. Retain only approved evaluation results locally and explicitly delete uploaded input/output files when policy permits; do not use Batch results to create live patient state. |

## PP and setup prompt caching

The patient-profile setup path now sends the complete bytes of `services/api/catalog/patient-profile.json` inside stable developer content, alongside the setup instructions. The Zod `PatientScenarioProfileSchema` remains the structured output contract. A regression test checks that the JSON content is sent intact and that the manually aligned `PATIENT_PROFILE_FIELDS` list still matches its 70 catalog entries. An explicit cache breakpoint ends after the catalog; the changing scenario seed is a later user message. The PP-derived generated response policy and per-field wording continue to serve patient-turn prompts, where stable policy precedes the changing learner/scenario JSON.

Caching can now reuse the stable setup instructions/catalog prefix and patient-turn policy prefix. Any schema, catalog, or prompt edit can change the prefix and cause a fresh cache write. The two synthetic setup responses confirmed 1,880 cached tokens per request after the prefix was warm. The Oct 6 14-token smoke request did not exercise cache eligibility. No session usage rows were present in the local database at that check, so there is no production hit-rate baseline yet.

## Initial evaluation plan

1. **Use existing telemetry first.** From `provider_usage`, group input, cached-input, cache-write, output, estimated cost, and duration by `operation`, model, tier, and prompt/schema version. Report cache-hit share only over eligible requests (at least 1,024 stable prefix tokens for GPT-6 Luna). Keep the tenant dimension available for internal budget analysis and avoid exposing another tenant's figures.
2. **Measure repeated sessions.** Run multiple synthetic setup and patient-turn sessions with the same prompt/schema version and different seeds/messages. Confirm that the first matching prefix writes cache and later requests report cached input. Compare estimated uncached versus observed cached input cost; do not infer provider billing from estimates alone.
3. **Set the Batch gate.** Before implementation, obtain educator approval for a versioned rubric and synthetic reference cases. Compare synchronous and Batch outputs on the same fixtures, join every result by `custom_id`, review clinical behavior blind to transport, and require the same quality acceptance criteria. Report cost and completion-time tradeoffs separately.
4. **Keep realtime gates.** Do not route learner-visible turns through Batch or Flex without a separately accepted latency/availability target. OpenAI's Fast mode costs more than Standard for GPT-6 Luna; lower price alone is not a reason to change the interactive tier.
