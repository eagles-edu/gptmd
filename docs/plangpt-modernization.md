## Clean-slate premise and decision summary

GPTMD is the implementation canvas, not a deployment that must preserve the legacy stack. Treat the checked legacy projects as evidence for the clinical-English practice flow, patient-profile fields, turn sequencing, and speech experience. Reuse useful assets and verified behavior; do not preserve old service boundaries, route names, `sid`/`did`/`aid`/`tid` fields, Flask/FastAPI, or the Assistant-era session shape. RedisJSON is retained for the required temporary active-scenario lifecycle and its 20-minute cleanup; that is a product requirement, not compatibility with legacy service boundaries. The history document remains the evidence record; this page and its diagram are the proposed product/system design.

The Assistants API was sunset on August 26, 2026, so every remaining Assistants integration must be removed. The newest legacy copy already calls Responses and Conversations, but the migration is incomplete: Python owns setup and conversation/TTS, the Express session manager retains Assistant-era field names and mode values, the browser sends those compatibility fields, and the current session documents mix app state with provider state.

Build a TypeScript application runtime for the server side, with Nuxt/Vue as the browser client and a standalone Express service in `services/api/` as the single application API. The API should be a modular monolith: setup, turn orchestration, session access, and speech generation share one deployable runtime and explicit module boundaries. Keep it separate from Nuxt as required by the repository contract. Use the official OpenAI Node SDK and Responses API; use Conversations for provider-managed turn context, and keep the application’s session, patient profile, turn ledger, and deletion policy authoritative in app storage.

The durable unit is one authenticated customer-owned patient session. At setup completion, the generated `PatientScenarioSeed` is validated and committed as immutable. It establishes the clinical case, answer key, supported results/findings, persona seed, and expandable history clues. During turns, the patient model may elaborate on a clue when the clinician asks; each accepted elaboration is validated and appended as a `PatientFactExpansion` before it is spoken. The session's patient-profile view is the seed plus those append-only expansions. This lets a clue such as “in recovery” unfold into a consistent substance-use history without rewriting the original case or forgetting details on later turns. Session state also tracks what the clinician has asked, what the patient has disclosed, assessment progress, exam/order state, and interaction mode. A model-generated utterance is not canonical until its fact expansions have been accepted and recorded by the application.

This is a maintainability and deployment simplification, not a promised model-latency improvement. The interaction is dominated by browser capture/playback and network calls to model and speech services. TypeScript does not remove those waits. Measure end-to-end and per-stage latency before and after each migration step.

## Proposed system shape

The new [target architecture diagram](plangpt-modern-system.svg) separates browser interaction, the TypeScript application API, durable application state, ephemeral coordination, and OpenAI-hosted state. Its editable D2 source is [`diagrams/plangpt-modern-system.d2`](diagrams/plangpt-modern-system.d2); `npm run diagrams:check` verifies that the published SVG is generated from that source.

### Browser client

After login, the signed-in home page links to Instructions, History-Taking Overview, Account Status (usage, metrics, downloads, and payment gateway), Contact Us, and Begin Visit. Begin Visit opens the encounter and its preflight/consent UI. Request microphone access after an explicit audio-mode action; if the user declines, retain the allowed text path. Explain local-data use, but store only non-sensitive preferences in browser storage. Keep the full patient profile, diagnosis, transcript, audio, and provider IDs server-side.

Keep Nuxt/Vue responsible for the patient screen, setup status, microphone permission, browser speech recognition, turn controls, and Web Audio playback. The browser sends recognized text and a client-generated turn/idempotency key to the application API. It never receives the OpenAI API key, Redis credentials, or a direct Redis URL. Do not expose a provider Conversation ID as an authority token; the server resolves provider IDs from the authenticated application session.

Use HTTPS for setup, session restoration, orders, exams, and assessment actions. Use the authenticated session API for each serialized Responses patient turn. Use the encounter LED to make turn ownership clear: the clinician speaks on green; yellow means the patient is processing or speaking; return to green after playback completes. An authenticated WebSocket is an optional transport for patient audio if measurement shows it improves delivery; Socket.IO is not a product requirement. Authorize every connection from the same server-side session or a short-lived connection ticket, and bind it to one patient session. The session cookie should be HTTP-only, Secure in production, SameSite-configured for the deployment topology, and rotated at session creation.

### TypeScript API service

Keep one independently deployable Express service under `services/api/`. Organize it as typed modules for HTTP/session/auth, simulation setup, conversation turns, OpenAI access, speech output, Redis coordination, persistence, and Socket.IO delivery. Share request/response schemas with the Nuxt client through generated OpenAPI types or a workspace package. Runtime-validate all network input and provider output; TypeScript types alone disappear at runtime.

The browser's existing patient API boundary uses runtime Zod contracts in `app/schemas/patient-api.ts`; `docs/schemas/` contains generated JSON Schema for those contracts, including the server-only full scenario profile. The patient profile example is [`gpt-patient-obgyn.json`](gpt-patient-obgyn.json). The API has a server-side module for structured full-profile generation and validation, but the Express service has no authenticated setup/session handlers and does not persist or activate the generated profile. Validate future route requests and provider outputs independently or move the contracts into a shared package before implementing those routes. Never treat a TypeScript annotation as runtime validation.

Use resource-oriented routes rather than leaking provider request shapes:

| Route | Purpose |
| --- | --- |
| `POST /api/sessions` | Create an app session and secure cookie. |
| `POST /api/sessions/:sessionId/setup` | Generate and validate the complete private patient profile; derive the five setup variables; create the provider Conversation. |
| `POST /api/sessions/:sessionId/turns` | Accept `{ turnId, text }`, append one turn, generate the patient response, and begin speech delivery. |
| `POST /api/sessions/:sessionId/orders` | Place an order from the scenario's supported test catalog. |
| `GET /api/sessions/:sessionId/orders/:orderId` | Read a pending or released result. |
| `POST /api/sessions/:sessionId/exams` | Start, continue, or complete an authorized abdominal or pelvic exam mode. |
| `POST /api/sessions/:sessionId/assessment` | Enter, submit, and complete the learner's assessment phase. |
| `GET /api/sessions/:sessionId` | Restore authorized session state after refresh/reconnect. |
| `DELETE /api/sessions/:sessionId` | Delete app-owned state and invoke provider-state deletion where supported by policy. |

The browser should not send `assistantId`, `threadId`, `chatId`, `dataId`, model names, or OpenAI request objects on every turn. The service binds the authenticated session to its data and provider IDs. Replace the `sid`/`did`/`aid`/`tid` compatibility vocabulary with one opaque app `sessionId`, an internal `conversationId`, and a per-turn `turnId`.

### Scenario seed, expandable patient profile, and encounter state

Create the **complete patient profile first**, before the first patient interaction. It is the private, canonical case for the session, not just the small profile card shown to the learner. Generate and validate the patient's identity, case-relevant history, current concern and symptoms, patient-reported beliefs, case truth, supported exam/test facts, diagnosis or explicitly unknown status, and stable communication traits as one coherent profile. The evolving canonical field catalog in [`services/api/catalog/patient-profile.json`](../services/api/catalog/patient-profile.json) describes what a profile can contain; it may grow and is not a checklist that every patient must fill. For each new field, define its meaning and type, decide required/optional/inapplicable behavior, and assess whether the schema version or stored profiles need migration. Define applicability for each scenario. Preserve the difference between a confirmed negative, an unknown fact, and a field that does not apply; record “not yet elicited” in encounter disclosure state rather than the initial profile. Do not invent irrelevant or sensitive history just to populate the catalog. The current canonical fields are `fullName`, `dateOfBirth`, `bodyType`, `reasonForVisit`, and private `diagnosis`; the client receives the same first four fields and does not receive `diagnosis`. These values retain their names across server and client boundaries. Use `dateOfBirth` and `bodyType` for image selection.

Validate every populated profile field and all cross-field constraints before saving the versioned, immutable `PatientScenarioSeed`; require fields according to that case's applicability rules. Compute age from DOB at the session's fixed start time. Reject or regenerate a 16-year-old profile that says the patient is menopausal, and reject or regenerate a 75-year-old profile that says the patient is pregnant; historical pregnancies must still have a coherent age and timeline. Validate the current concern, relevant history, diagnosis, supported results, and examination findings against one another. Setup retries must be idempotent and must not silently create a different patient. Store the random seed, schema version, prompt/rubric version, and generation model for reproducibility. Do not overwrite the profile during a live encounter. Corrections to case-defining truth require a new scenario version before the encounter or a new session.

The full seed includes the patient's stable identity/profile, current condition and onset/course, associated symptoms and relevant negatives, complete relevant gynecologic/obstetric and general history, medications/allergies, patient beliefs, relevant examination findings, supported diagnostic tests and their deterministic results, and the case's intended diagnosis or explicitly unknown diagnosis. Separate clinician-hidden answer-key facts from what the simulated patient personally knows. The doctor should not see the answer key before submitting an assessment. The five setup values are a small projection of this richer profile, not the complete case.

The setup sequence has two distinct stages. First, generate and validate the complete private profile. Then derive the five internal values from that exact saved profile, without a second model call. This preserves one patient identity and one coherent case. DOB determines the age band and body type selects the matching portrait. The learner receives only the four client-safe values—name, DOB, body type, and reason for visit—and no diagnosis. The existing four-field Zod response contract is the intended learner-facing boundary; maintain separate full-profile and internal-projection contracts.

Validate age-dependent facts using age at the session's fixed start time. Reject or regenerate a profile that marks a 16-year-old as menopausal or a 75-year-old as pregnant. Historical pregnancies must have a plausible age and coherent timeline. Validate the entire case before deriving the five variables or selecting an image.

The complete profile is available to the server from setup, but the learner should hear only the facts that fit the question, phase, and disclosure rules. Do not read the profile aloud as a checklist or reveal the hidden answer key. A profile can contain a complete substance-use history, for example; the patient discloses it naturally when asked. If a later turn needs a detail the profile intentionally left open, the model may propose a compatible elaboration; validate and append that expansion before speaking it, then reuse it consistently. Fixed case truth and already accepted details cannot change.

Some histories need a much richer account than a single cue. For example, an obstetric history may unfold as: “I’ve been pregnant seven times: one stillbirth, two miscarriages in the first trimester, and four normal births. I have four healthy children. I also had eclampsia during one pregnancy.” Keep the arithmetic coherent (one + two + four outcomes equals seven pregnancies) when all pregnancies have ended. Gravidity includes an active pregnancy, so when the patient is currently pregnant, completed outcomes must total one fewer than the pregnancy count. Retain the complication, and let the patient naturally fill in omitted details such as timing, gestational age, or which pregnancy had eclampsia when asked or when relevant to the answer. Such elaboration may add plausible, age-appropriate details that complement the seed; it must not contradict the seed or any previously accepted fact, create impossible chronology, or break outcome and child-count consistency. Validate any generated gestational-age detail or parity shorthand against the individual outcomes and the application's configured conventions, but do not reject a coherent elaboration merely because the seed left that detail open. Once stated, save it in the append-only obstetric-history section and reuse it consistently on later turns.

Record the epistemic source of each expansion. Pt's may incorrectly attribute and/or report diagnoses, etiology, genetics, folklore, and other beliefs regarding themselves. So, consider a newly generated history detail is a simulated patient-reported statement with the presumption of regularity, albeit guarded, not as an observed or verified medical certainty or result. For example, “I was told I have hepatitis B” can be added as patient-reported history whether it coheres with the pt profile or not; do not turn it into a newly invented confirmed lab result. Rather, confirmed results come only from the scenario's supported test/result catalog. Expansions may add relevant history, including a reported comorbidity, but cannot silently replace the seed's intended primary diagnosis, deterministic results, or rubric. Debrief may use the expansion ledger to assess whether the learner elicited and recorded a newly disclosed history fact. Keep spoken language patient-centered even if a legacy seed uses stigmatizing shorthand.

Cases are fictional training scenarios, not patient records or clinical decision support. The generator must not use real patient data as seed material; customer identity and account records remain separate from the simulated patient identity.

Generate personality at setup as bounded, stored traits rather than a free-form adjective: for example, communication style, anxiety/guardedness, verbosity, health-literacy level, and willingness to volunteer information. Randomize once using a recorded seed and keep those traits fixed for that session. Personality changes how the patient communicates, never the clinical facts or result values.

Persist mutable encounter state separately from the immutable scenario seed:

| State | Purpose and invariant |
| --- | --- |
| `phase` | Finite state such as `intake`, `history`, `assessment`, `abdominal_exam`, `pelvic_exam`, `orders_pending`, `results_review`, `complete`; transitions are validated by the API. |
| `factExpansionLedger` | Append-only facts created from expandable scenario clues during turns, with section, normalized detail, source/certainty, originating turn, and prompt/model version. For obstetric history, preserve individual pregnancy outcomes, compatible elaborations, and known complications alongside the reported total; validate chronology, age-appropriate plausibility, and outcome/child-count consistency. Accepted facts are session-authoritative and reused on later turns; they never overwrite the scenario seed. |
| `disclosureLedger` | Seed and expansion fact IDs already revealed, with the turn/action that revealed each fact. Patient responses may reveal known facts when appropriate to the question or mode; new expansions are committed with their disclosure event before the reply is delivered. |
| `coverage` | Required history/assessment topics asked or still missing; tracks the learner's information gathering without treating every checklist item as a diagnosis. |
| `orders` | Requested test, order time/status, and result reference. Only scenario-supported tests can be ordered; results come from the scenario's fixed result set, not a fresh model invention. |
| `exams` | Consent/decline, exam type, phase, permitted findings, and completion. Abdominal and pelvic modes have separate state and scenario-defined findings. No findings are returned for an exam that was not completed. |
| `assessment` | Learner's stated summary, differential or diagnosis, rationale, and plan; scored against a versioned educator-reviewed rubric after submission. |
| `eventLedger` | Ordered append-only session events for turns, phase transitions, orders/results, exam actions, mode changes, and completion. It is the app audit/replay source, separate from provider Conversation history. |

Model instructions carry the session's current phase, personality, relevant seed facts, accepted expansions, and disclosure boundaries. For an asked-about history cue, the model may return both a natural patient utterance and proposed fact expansions in structured output. The API checks for contradictions and chronology errors, records new health history as patient-reported unless it is a seeded/verified finding, and protects the seed's primary case truth and deterministic results. It then atomically appends approved expansions and turn/disclosure events before delivering the response. On validation failure, retry with the existing profile or use a safe clarification response and record the failure. Model tool calls may propose supported actions, but only the API may authorize orders, publish seeded test results, change exam state, or advance the phase.

The educational objective is for the doctor to elicit enough information to understand the current condition, pertinent history, and diagnosis when one exists. Use a configurable, educator-reviewed coverage rubric for symptom onset/course, location/character/severity/timing, aggravating and relieving factors, associated symptoms and relevant negatives; scenario-relevant menstrual, obstetric, sexual/reproductive, contraception and pregnancy context; medical/surgical history, medications/allergies, family/social factors and patient concerns; then exam/test findings, synthesis, differential/diagnosis, rationale, and plan. Each case marks which topics matter and which are irrelevant or sensitive, so the rubric rewards pertinent assessment instead of asking every patient every question. Sensitive history should be patient-centered, non-assumptive, and appropriate to the case; the [CDC sexual-history guide](https://www.cdc.gov/sti/hcp/clinical-guidance/taking-a-sexual-history.html) emphasizes tailoring questions and not pursuing disclosure beyond the patient's comfort, while [ACOG's initial reproductive-health visit guidance](https://www.acog.org/clinical/clinical-guidance/committee-opinion/articles/2020/10/the-initial-reproductive-health-visit) supports open, nonjudgmental discussion. Do not prematurely reveal the hidden diagnosis. On completion, compare the learner's submitted assessment with the case rubric and provide actionable feedback; do not interrupt every patient turn with grading feedback. Scenario content and rubrics need clinical educator review before release.

Assessment and examination transitions must be explicit. Provide accessible UI controls and support concise spoken cues such as “begin assessment” and “complete assessment”; confirm the transition before changing phase when recognition is ambiguous. Completing the assessment closes that phase and triggers feedback/debrief; it does not delete or rewrite the scenario seed or accepted history expansions. Abdominal and pelvic exam modes must be scenario-indicated, explicitly requested, and consent-aware; preserve consent/decline and chaperone state where the scenario requires it, and return only findings permitted by that scenario and completed mode. The patient can decline or stop an exam. ACOG notes that an internal pelvic exam is not routinely required at an initial reproductive visit absent an indication, so the case rubric must reward appropriate clinical judgment rather than exam completion by default. Voice cues are conveniences, with visible controls as a reliable fallback.

### Customer authentication and controls

Authenticate customer users through an OIDC-compatible identity provider; keep the provider behind an application auth adapter so it can be changed without changing session ownership. Model organization/customer, user, role, entitlements, and app session separately. Every session and event is tenant-owned and authorized server-side; use tenant-scoped database queries and deny cross-customer access by default. Roles should cover learner, instructor, and customer administrator.

Customer administrators control enabled model tier, audio modes, per-user/session quotas, transcript retention, and whether exam/order features are available. Record the tier and mode selected at session start with the customer's policy version. A tier is an entitlement and budget choice, not a clinical quality guarantee. Do not allow a browser to select an arbitrary model ID or override account limits.

### Responses API and turn state

Use the official OpenAI JavaScript/TypeScript SDK from this backend only. Create a Conversation before requesting the full profile, then send the structured profile-generation request to Responses with that Conversation ID. After validating and saving the profile, use the same Conversation for patient turns. Each Response uses the provider's saved Conversation items as context, then automatically adds the request and response to that Conversation; do not manually resend the transcript or also supply `previous_response_id`. Read text using the SDK's `output_text` helper where suitable, but validate structured output and inspect refusal/incomplete/error states instead of assuming every response contains usable text. The [Assistants migration guide](https://developers.openai.com/api/docs/assistants/migration) directs new interactions to Conversations and Responses and says migrated history must come from application-stored messages. The [conversation state guide](https://developers.openai.com/api/docs/guides/conversation-state) documents durable provider-side conversation items and stateless/manual alternatives.

For setup, use Responses Structured Outputs with a strict versioned JSON Schema for the full `PatientScenarioSeed`: display profile; complete patient-known history; clinician-hidden case truth and diagnosis/unknown status; fixed exam findings; supported order/result catalog; persona traits and seed; and rubric/version references. Generate this complete profile first, validate it, and only then derive the five setup variables from it. Use a separate structured turn output for spoken reply plus zero or more proposed `PatientFactExpansion` records. Validate schema and cross-field consistency in application code. Structured Outputs constrains shape; it does not establish that a generated detail is consistent with this session. Keep presentation fields such as name, age/DOB, chief complaint, and body type distinct from hidden answer-key facts. The legacy five-field object is the visible profile projection, not a sufficiently complete seed/profile contract. The active GPTMD runtime still has only a four-field response schema; its current legacy-style prompt/JSON handling must become an enforceable backend contract. See [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Nuxt008 provides the historical client-side reference for the five-value setup and portrait lane: its `AppSection.vue` requests the five profile variables, parses them into client state, and on room entry calculates age from DOB and combines the age band with body type to choose the image. The Nuxt008 repository does not contain the called setup backend, so its client source cannot establish whether that backend first created a full profile. GPTMD makes the intended order explicit and improves the boundary: the backend creates and validates one complete profile, derives the five values from that profile, saves both under the same session, and returns only the learner-authorized projection. It also rejects age/history contradictions before image selection, rather than trusting model-produced fields or substituting `N/A` for missing values.

Create exactly one app encounter and one provider Conversation per patient session, starting before full-profile generation. Persist the provider `conversationId` internally, tied to that app session and tenant. On reconnect, resume the same state or reconstruct provider context from the app event ledger; never attach another patient's seed, expansions, or history. The app's immutable scenario seed, accepted fact-expansion ledger, encounter snapshot, and append-only event ledger remain canonical for state, access control, replay, and audits. The migration guide specifically says prior history must be supplied from messages stored by the application, so provider state cannot be the sole recovery copy. Responses are stored by default; the Responses guide says `store: false` disables response storage, while the create reference says stored response data is retained for at least 30 days subject to data-retention exceptions. Choose storage settings and deletion behavior only after setting the product's retention and account-data policy; synthetic simulation data still needs a documented lifecycle. See the [Assistants migration guide](https://developers.openai.com/api/docs/assistants/migration), [conversation state guide](https://developers.openai.com/api/docs/guides/conversation-state), [Responses migration guide](https://developers.openai.com/api/docs/guides/migrate-to-responses), and [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create).

The stateful API saves GPTMD from rebuilding the full prompt history, but it does not remove that history from model processing. The [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) says Conversation items are prepended to each request and new input/output items are appended after completion. Budget for growing input context, measure cached and uncached token usage, and define an application-owned context-management policy before a long scenario approaches the model limit. Conversation state is the provider's working copy; PostgreSQL and Redis remain the app's source for restoring the exact patient and accepted events.

Keep model instructions, schema versions, model selection, timeout/retry policy, and feature flags in server-side versioned configuration. Do not depend on a live Assistants object. The migration guide's suggested dashboard prompt replacement is not a durable default here because its own note warns reusable prompts have a separate deprecation timeline.

### Setup lane, turn lane, and model tiers

The original premise—separating setup from patient turns to handle expected user load—is sound as a workload distinction. Setup occurs once per patient session and can tolerate a bounded queue and longer timeout. Conversation turns are interactive, latency-sensitive, and must serialize within a single patient session. Give these lanes separate concurrency limits, queue budgets, timeouts, retry policies, and observability from the beginning. Setup saturation must not consume all capacity needed for active patient turns.

That does **not** mean two Express services or two AI vendors are required. Start with one modular TypeScript API and the same Responses API integration, using separate internal policies and bounded worker/queue capacity for setup, live turns, and post-session assessment scoring. Scale the API horizontally across customers while a per-session lock preserves one active patient turn. Add a dedicated worker pool/deployment only if load tests show setup or scoring work harms turn latency. Separate API keys/projects/providers do not automatically increase capacity; use them only when account-level limits, billing ownership, or measured quotas require isolation and verify the provider's current rate-limit policy first.

The likely bottlenecks are model wait, chained speech generation, queue contention, and single-session sequencing—not the TypeScript HTTP handler. The legacy workflow waits for a complete response and then serially requests TTS for sentence chunks, adding provider round trips. Stream Responses output and synthesize clauses as they complete, or use Realtime Full Audio when case-fidelity evaluation passes. Preserve one active turn per session because that is a correctness invariant; widen capacity across independent sessions with bounded concurrency, back-pressure, and horizontally scaled stateless API instances. Pre-generate or queue setup cases where the product flow allows it. Measurements should decide whether setup workers, turn workers, provider quotas, or audio relay need separate pools.

Offer three named model tiers, with server-side model aliases that administrators can remap after evaluation:

| Customer tier | Intended use | Model |
| --- | --- | --- |
| Luna | Recommended default: strongest cost/quality choice for this product under the current 3% practical tolerance. | GPT-6 Luna |
| Terra | Optional higher-cost tier; use when case evaluations show a meaningful benefit for the intended cases. | GPT-5.6 Terra |
| Sol | Optional premium tier; use when case evaluations show a meaningful benefit for the intended cases. | GPT-6 Sol |

OpenAI does not publish enough training-corpus detail on these model pages to rank Luna, Terra, and Sol by the amount or quality of medical material in their training data. Public medical-performance evidence is a proxy, not a corpus inventory. In OpenAI's [HealthBench system-card results](https://deploymentsafety.openai.com/gpt-6-astra/protocolqa-open-ended), the currently selected variants score as follows (length-adjusted; higher is better):

| Model variant | HealthBench | HealthBench Hard | HealthBench Professional | HealthBench Consensus |
| --- | ---: | ---: | ---: | ---: |
| GPT-6 Luna | 54.5 | 31.4 | 60.8 | 95.9 |
| GPT-5.6 Terra | 57.0 | 32.7 | 57.7 | 95.1 |
| GPT-6 Sol | 53.2 | 30.1 | 60.8 | 96.2 |

Use the requested 3% error margin as the practical decision tolerance. Luna is the recommended default because it wins the product's cost/quality equation within that tolerance; do not select a more expensive tier based on small public benchmark differences alone. The published point scores reverse order by benchmark, and their raw spread reaches 3.8 points on HealthBench (Terra versus Sol); the cited table supplies no confidence intervals, so it does not establish that every result falls inside a 3% statistical margin. These scores do not reveal the models' training corpora or directly evaluate this app's standardized-patient interaction. Keep Terra and Sol available as optional tiers, and promote them for a case or customer only when same-case educator evaluations show a meaningful quality benefit worth their added cost. Evaluate canon adherence, appropriate disclosure, personality consistency, assessment coverage, refusal behavior, response time, and total cost per completed session. Freeze the selected tier for the session so patient character behavior does not switch unexpectedly. Keep the setup/canon-generation model independently configured, and do not let a learner's lower-cost interaction tier weaken the case facts or rubric. See the official [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra), and [Sol](https://developers.openai.com/api/docs/models/gpt-6-sol) model pages.

Model tier and interaction mode are separate choices. The intended encounter is voice-first: use consistent cross-browser STT for short live questions, send finalized text through the authenticated Responses patient-turn lane, and play the patient's spoken reply before returning the green turn light. OpenAI's [Realtime transcription guide](https://developers.openai.com/api/docs/guides/realtime-transcription) describes browser WebRTC for live transcription; create the session with a server-minted ephemeral credential so the provider key remains server-side. Standard browser `SpeechRecognition` is an optional editable, single-question convenience, not the cross-browser solution. Use file transcription for occasional longer audio. A typed transcript can remain an explicit fallback during development, but it is not the intended primary experience. Keep private scenario seed and undisclosed patient history out of browser-visible provider instructions.

Choose modality at session start and keep it stable for the encounter by default. A Responses `conversationId` and a Realtime `sessionId` represent different provider contexts; persist provider type and ID separately and never assume state can be transferred between them. If mid-session modality switching is later required, make it an explicit transition: checkpoint the app event ledger, close the old provider context, start the new context, and reconstruct only the authorized encounter projection and transcript. Record that transition for replay and evaluation.

For the normal voice encounter, send live audio only for transcription, keep the finalized transcript and patient reply in the encounter record, and do not retain raw microphone audio by default. A spoken “Please write that down” request displays the patient reply as a written note. Patient and clinician can both ask for repetition, louder/slower/simpler speech, another explanation, spelling, or written words when communication breaks down. The LED governs turns; do not listen for an ordinary new clinician turn over patient playback. A typed transcript may be offered as an explicit fallback, not the primary interaction. If a future full-audio mode is prototyped, treat it as a separate proposal and preserve the same visible turn-taking behavior and privacy boundary.

### Session state, Redis JSON, archive, and retention

Use PostgreSQL for the lasting client/session history, completed-turn records, provider usage, download activity, and success tracking. Save related changes together so a turn cannot be half recorded. Keep the original patient scenario unchanged after the session starts; add newly disclosed patient facts as separate history entries. Store the patient scenario as validated structured data and put searchable details such as owner, status, and timestamps in regular database columns. PostgreSQL is the durable history used for client records, archive creation, and rebuilding an active session if Redis data is lost.

During a scenario, Redis JSON should hold the live patient profile and current session state. The API reads and updates that copy as the learner proceeds; it is shared working state, not a disposable cache. Redis can save its data to disk and keep a second server ready, which helps restore an active session after a restart or machine failure. Those protections have settings and limits: periodic snapshots can miss recent changes, saving every write is slower, and Redis copies changes to a second server asynchronously, so a sudden failover can still lose a recent update. Choose the acceptable loss window, configure disk persistence and backups to meet it, and verify recovery.

At the end of each learner/patient exchange, add a compact history entry containing the turn ID, the two messages, any newly disclosed facts, and the resulting session version. This preserves the conversation and gives the system a way to rebuild Redis if needed; it does not copy the entire live profile into PostgreSQL on every change. PostgreSQL's write-ahead log records those changes without writing every affected database page at each commit. A periodic profile snapshot can make recovery from the history faster. If a browser retries a turn, use its turn ID to return the already-saved reply instead of creating a second one.

The two systems have distinct recovery roles: Redis restores the fast, current session from its saved data; PostgreSQL can rebuild that session from completed exchanges if Redis data is lost. Keep each completed exchange in a Redis Stream as part of the live-session update. A dedicated PostgreSQL worker copies events from that stream into the long-term history, then acknowledges them only after the database commit succeeds. Give every event a stable ID so retries cannot create duplicate turns. The worker must never hold up the learner's response. If PostgreSQL is temporarily unavailable, the stream buffers events until the worker can catch up; alert on its age and size, and stop admitting new sessions before it can fill. Keep pending events until PostgreSQL confirms them, even though the Redis JSON session document expires 20 minutes after completion or cancellation. The existing `redis` Node package can read/write JSON and Redis Streams. Redis Stack already provides these features; Redis 8 also includes JSON support, so an upgrade is an option after its behavior and recovery are checked.

### Keep background work off the patient response path

The learner-facing request should wait only for work needed to produce and safely retry the patient response: authentication, the current Redis session state, the model response, and one Redis commit containing the updated live state, accepted reply, retry key, and recovery event. This is payload-critical state, not a separate reporting operation. Do not wait for PostgreSQL, usage accounting, analytics, archive creation/upload, download metrics, notifications, cleanup, or any worker to finish. A JavaScript operation being asynchronous does not remove request latency if the handler still `await`s its completion.

Set a strict boundary: the response never waits for side work or worker completion. Dispatch must be nonblocking; the 5 ms limit is a ceiling on handoff overhead, not time the handler may spend waiting for a side operation. Run PostgreSQL writers, archive generation, metrics, and cleanup in separate worker processes with bounded queues and retries. Use worker threads only for CPU-heavy tasks such as archive compression; database and object-storage I/O can use asynchronous worker processes. Measure queue handoff, worker lag, Redis transaction time, and end-to-end response time separately. If the queue approaches capacity, reject new work quickly rather than making an active learner wait behind background work. Keep Redis Stream entries until PostgreSQL confirms them, and monitor retention because a long PostgreSQL outage can extend the time that pending event data remains in Redis.

On completion or cancellation, update Redis session state, set its absolute 20-minute expiry, and queue a terminal event without waiting for PostgreSQL. A background worker records the terminal state and unique archive job in PostgreSQL, then another worker builds and verifies the patient-profile, transcript, captured-audio, and debrief archive from PostgreSQL records plus separately retained audio. The API reports that the archive is preparing until the worker confirms it is ready. PostgreSQL keeps client/session records, stats, provider usage, download engagement, and success tracking. Record download authorization separately from confirmed transfer completion: issuing a signed URL does not prove that the client received the archive, so capture completion from an API-proxied transfer or storage access events when available. Keep signed URLs short-lived and private because they are bearer credentials. Store product events in PostgreSQL with retention and aggregation appropriate to their measured volume; add a separate analytics system only if benchmarks show PostgreSQL is no longer the right fit. Metrics and download tracking must not delay the response that requested them.

Use two independent deadlines anchored to the terminal timestamp. When a session ends, one Redis transaction marks it complete, sets the JSON session's absolute 20-minute expiry, and adds a terminal event to the stream. A background worker records that event and a uniquely keyed archive job in PostgreSQL. It processes events in session order and starts archive creation only after the terminal version and all earlier turns have reached PostgreSQL. Archive downloads may be initiated through terminal time plus 72 hours. Enforce that cutoff on every download request and issue short-lived URLs only after client/tenant authorization, with URL expiry capped at the remaining window. A transfer authorized before the cutoff may finish afterward; stopping it exactly at the deadline requires streaming through the API. Object-storage deletion is cleanup and may be asynchronous; it is not the access control. Workers retry safely; the stream retains unconfirmed events until PostgreSQL acknowledges them, separately from the 20-minute JSON key expiry. Track and alert on queue age, queue size, and overdue cleanup. Audio capture and download require explicit consent and policy. Do not report an archive ready until its contents and metadata are verified.

Persist transcript events with speaker, timestamp, phase, modality, and turn ID so recovery and debrief generation have a durable source. Include the transcript and captured audio in the 72-hour client archive; stage audio outside RedisJSON and retain it only as long as the archive workflow/policy requires. Store test results and exam findings as references to fixed scenario-seed facts rather than copying model prose as truth. Preserve generated patient-reported expansions in their own ledger so the debrief can distinguish seeded case facts from details improvised during the encounter. Keep the profile/case answer key available only to authorized instructors or after learner submission/debrief.

Require Redis JSON for the live patient/session state and Redis Streams for the event handoff in every deployment. Redis Stack 7.4 provides both locally; Redis 8 includes JSON and Streams. Keep Redis private and backend-only. Configure memory limits, persistence, backups, event-stream retention, bounded worker queues, retries, recovery, and fast overload rejection before launch. Keep unrelated pub/sub and rate-limit uses out of the request path unless measured needs justify them. RedisInsight is an operator tool, never a request-path dependency.

Technology references: [Redis JSON data type](https://redis.io/docs/latest/develop/data-types/json/), [Redis 8 capability availability](https://redis.io/docs/latest/operate/rc/databases/configuration/advanced-capabilities/), [Redis key expiration](https://redis.io/docs/latest/develop/using-commands/keyspace/), [Redis persistence and its loss/performance tradeoffs](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [Redis replication and failover limits](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/), [node-redis JavaScript guide](https://redis.io/docs/latest/develop/clients/nodejs/), and [PostgreSQL write-ahead logging](https://www.postgresql.org/docs/current/wal-intro.html). For an S3-compatible artifact store, the application must enforce archive access expiry because [presigned URL semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html) govern individual requests and [lifecycle deletion](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html) can run asynchronously.

### Speech and real-time flow

In Transcript mode, the browser sends recognized or typed text over HTTPS. The API authenticates the request, takes the per-session turn lock, reads the live Redis session, calls Responses with the relevant scenario seed and accepted profile expansions, and validates the patient reply and proposed facts. It then updates Redis and appends the completed-turn event to the Redis Stream in one transaction, and returns the reply without waiting for PostgreSQL. A background consumer writes the event to PostgreSQL and acknowledges it after commit. A repeated turn ID returns the saved Redis reply; PostgreSQL's unique event ID makes worker retries safe. Optional speech synthesis streams audio separately. Do not accept the next turn until the prior patient response and any enabled audio playback are complete.

In Full Audio mode, the API bridges browser audio to a Realtime session, authorizes actions against the same encounter state machine, and records final transcripts, phase cues, and action events in Redis session state and the event stream. Background workers copy those events into PostgreSQL. A Realtime disconnect must not lose the recoverable encounter state or permit a duplicate turn. Keep provider context IDs separate from the app's session ID.

Instrument browser capture, API queue/lock, Responses first token/completion, TTS first byte/completion, WebSocket delivery, Realtime first audio, and playback completion. Compare complete-response TTS with clause-level streamed synthesis and Full Audio under the same scripted cases. Do not optimize by parallelizing multiple patient turns; the simulation deliberately serializes them within each session.

## Is a pure TypeScript server advantageous and performant?

**Recommendation:** Yes for the application server and shared API contracts; no claim that it makes OpenAI generation faster.

| Area | TypeScript end state | Practical effect |
| --- | --- | --- |
| Shared contracts | Nuxt and Express share generated schemas/types. | Fewer hand-maintained payload translations; runtime validation is still required. |
| Service operations | One Node server process replaces multiple Python setup and speech services. | Fewer images, health checks, ports, dependency sets, and cross-service failure modes. |
| OpenAI integration | Official Node SDK and Responses types live beside routing/orchestration. | Less raw HTTP and manual payload parsing than the current Python bridge. |
| Runtime speed | Node async I/O handles concurrent HTTP/socket workloads efficiently. | Likely adequate, but no improvement is established without workload benchmarks. Model, network, TTS, and audio playback dominate perceived turn time. |
| Lost strengths | Python/FastAPI/Pydantic has strong request modeling and may suit future Python ML/audio work. | Preserve Python only for a demonstrated Python-only capability; do not keep it solely for historical continuity. |
| Failure risk | One API owns more functions. | Use module boundaries, separate worker/queue only if measured load requires it, and establish health, timeout, back-pressure, and tracing behavior. |

The migration is most advantageous if TypeScript becomes the single backend implementation language and the current service boundaries are consolidated into one modular API. Rewriting each Python endpoint one-for-one into a separate TypeScript microservice would keep most operational overhead while adding migration risk. Keep Nuxt and Express as separate deployables; this follows the current repository contract and preserves an API boundary for browser security and future workers.

## Deployment target

For local development, Docker Compose should run the Nuxt client, standalone TypeScript API, PostgreSQL, and a Redis deployment with JSON capability. Keep the current Redis Stack instance until a controlled Redis 8 upgrade proves JSON commands, persistence, expiry, and recovery behavior. Keep the private 72-hour archive destination explicit in the environment design. Expose only the web entry point to the host; bind data services to the Compose network and keep credentials in ignored environment files or a secret manager. Use health-gated dependencies and named volumes locally.

For production, build immutable Nuxt and API images, pin base/runtime images, terminate HTTPS at the ingress proxy, and keep PostgreSQL/Redis private on managed or separately operated infrastructure. Route `/api`, SSE, and the authenticated audio WebSocket to the API service. Scale API replicas statelessly; use Redis-backed WebSocket coordination only when more than one replica is needed. Configure liveness/readiness, graceful socket drain, request size limits, origin/CSRF protections for cookie-authenticated routes, rate limits, structured redacted logs, and request/turn correlation IDs. Never log patient turns, API keys, cookies, or audio payloads by default.

## Greenfield build sequence and acceptance gates

1. **Case and encounter contract:** define the immutable PatientScenarioSeed schema, expandable history sections, patient-reported fact-expansion schema, seeded personality, fact disclosure rules, phase state machine, exam/test catalog, coverage rubric, event types, and retention policy. Review representative seeded and dynamically expanded cases with medical educators before building generation.
2. **Customer control plane:** implement OIDC sign-in, tenant ownership, roles, model/audio entitlements, quotas, and transcript settings. Verify cross-tenant access is denied.
3. **State and setup lane:** add PostgreSQL constraints for immutable scenario seeds and append-only expansions/events; implement idempotent case setup with structured output and validation. Verify retries preserve exactly the same seed.
4. **Interactive text lane:** implement Responses turns with one active turn per patient session, idempotency, validated on-demand profile expansion, progressive disclosure, transcript projection, and separate setup/turn capacity limits. Verify accepted expansions survive reconnects and remain consistent in later answers.
5. **Clinical actions and debrief:** implement supported test orders/results, consent-aware abdominal/pelvic exam phases, spoken/UI assessment entry and completion, rubric scoring, and learner feedback. Verify no unsupported result or finding can be created.
6. **Voice conversation:** build the seven-second auto-submit and LED turn-taking loop first; use cross-browser Realtime transcription for short questions, Responses API for patient turns, and file transcription for occasional longer audio. Keep raw audio off by default. Standard browser recognition stays an optional one-question convenience.
7. **Deployment and scale:** ship Nuxt and the TypeScript API as separate images with PostgreSQL, Redis JSON capability, an idempotent terminal outbox/worker, and private 72-hour artifact storage. Add a dedicated worker only if load evidence supports it. Upgrade the Redis distribution only after compatibility and recovery tests pass; preserve the required session, TTL, archive, and recovery behavior.
8. **Evaluation/performance gate:** run educator-authored case evaluations for seed consistency, expansion coherence, timeline consistency, progressive disclosure, personality stability, assessment coverage, order/exam correctness, and debrief quality. Load-test setup concurrency separately from active turns; measure p50/p95 first-token/first-audio and full turn latency, provider usage/cost, CPU/memory, and reconnect behavior. Any quality or speed claim must come from these measurements.

### Frontend migration checkpoint

The legacy Nuxt/Vuetify frontend has been moved into GPTMD's Nuxt 4 application structure. The encounter landing page now presents a patient profile card and transcript interview shell, and the public `about`, `commands`, `help`, and `tutorial` pages use the migrated site layout. Legacy patient portrait, logo, and font assets are available under `public/assets/`. The front end uses typed, runtime-checked request/response shapes for the planned session, setup, and turn routes; those patient-session routes are not implemented by Express, so encounter requests report that limitation instead of pretending to complete a session.

The deployment uses Nuxt hybrid rendering. The generic encounter shell and public information pages are prerendered; browser interaction, microphone access, and API calls run after client hydration. Microphone APIs are only accessed in response to browser-side actions, so the encounter page does not need to disable server rendering. `nuxt build` remains the deployment command so Nitro can serve prerendered pages alongside runtime routes. `nuxt generate` is a static-only output and cannot provide this hybrid behavior. The Express API remains an independently built Node service. Node 24 is selected as the aligned runtime, while TypeScript 6 is kept across the frontend and API because the frontend lint/type tooling does not currently accept TypeScript 7.
